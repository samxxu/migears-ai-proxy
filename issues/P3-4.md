- 2026-10-01 · `owner — migears-ai-proxy` · `question` — re-checked against the code and **reproduced**, so the finding holds; but every fix for it forks on a behaviour change, so the call is the user's, not mine.
  - Reproduced, not static. A raw-socket server in `/tmp` (outside the repo) answers a POST with `HTTP/1.1 200 OK` + `Connection: close`, no `Content-Length`, no `Transfer-Encoding`, writes `data: {"choices":[{"delta":{"content":"partial` and closes with the body unfinished. Driven through the module's own `vendor/autoload.php`: `Upstream::post()` returns normally, `OpenAiClient::chat()` returns normally, and `Proxy::stream()` therefore emits the `[DONE]` / `event: done` sentinel (`src/Proxy.php:66`) — a truncated relay presented as a finished one.
  - The other two framings do not have the gap, and the same probe shows it: with `Content-Length: 100` and 21 bytes sent the call throws `CURLE_PARTIAL_FILE` (18, "end of response with 76 bytes missing"); with `Transfer-Encoding: chunked` and an unfinished chunk it throws 18 ("transfer closed with outstanding read data remaining"). So a truncation is surfaced whenever the protocol can express one. That falsifies the reporter's hedge "not reachable with real SSE upstreams": close-delimited is ordinary HTTP/1.1 framing (RFC 7230 §3.3.3 — with neither `Content-Length` nor chunked, the body ends where the connection does), and for curl the last body byte and EOF are the same event.
  - So the only place the gap can be closed is the SSE layer, and closing it is a behaviour change: treat a stream that never carried `data: [DONE]` as incomplete (throw instead of emitting `event: done`). That changes `Proxy` / `OpenAiClient` behaviour for every provider that ends a stream by closing without a `[DONE]` sentinel — and the module cannot tell such a provider from a truncated one either.
  - **Decision needed (coordinator / user):** is `data: [DONE]` mandatory for a stream to count as complete — throw on its absence, the strict reading — or is a clean close a legitimate end, keeping today's behaviour and leaving the caller to relax it? Either answer lands as one small change here; I am not choosing it for you because it moves public behaviour.
  - Level: filed P3 behind the "not reachable" hedge the probe falsifies. On impact I would grade it **P2** — a silent wrong result (an answer relayed as complete) — under "grade by what breaks for the user, not by how exotic the path". Front matter left as filed; flagging it here for the next filing.

    - 另两种分帧没有这个缺口，同一探针可见：`Content-Length: 100` 而只发 21 字节时抛 `CURLE_PARTIAL_FILE`（18，"end of response with 76 bytes missing"）；`Transfer-Encoding: chunked` 且分块未写满时抛 18（"transfer closed with outstanding read data remaining"）。也就是说，只要协议能表达截断，模块就会报出来。这推翻了立案时「真实 SSE 上游不会走到这里」的说法：以连接关闭定界是普通的 HTTP/1.1 分帧（RFC 7230 §3.3.3——既无 `Content-Length` 也非 chunked 时，正文长度由连接关闭界定），而对 curl 来说最后一个正文字节与 EOF 是同一件事。
    - 因此唯一能补上这个缺口的地方是 SSE 层，而补上它就是行为变更：把从未出现 `data: [DONE]` 的流当作不完整（抛异常，而不是发 `event: done`）。这会改变 `Proxy` / `OpenAiClient` 对每一个「以关闭连接而非 `[DONE]` 哨兵结束」的提供方的行为——而模块同样无法把这种提供方与被截断的情形区分开。
